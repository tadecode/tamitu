## Podsumowanie

`serviceAccountFor()` zwraca teraz pełny adres `<nazwa>@<projectId>.iam.gserviceaccount.com`, a `projectId` bierze z `GCLOUD_PROJECT` (walidacja formatu, wyjątek przy braku lub złym formacie – bez konta domyślnego). Poprawka trafia w przyczynę błędu i działa tak samo jak wbudowane rozwijanie skrótu w SDK. Brak ustaleń blokujących.

## Dowód: `GCLOUD_PROJECT` w analizie kodu i w runtime

**Przyczyna błędu (potwierdzona w źródłach).** W `firebase-functions` 7.4.0 opcja `serviceAccount` trafia do manifestu funkcji v2 **bez rozwijania skrótu** (`lib/v2/options.js`, `optionsToEndpoint`: `convertIfPresent(endpoint, opts, "serviceAccountEmail", "serviceAccount")` – bez konwertera; rozwijanie `serviceAccountFromShorthand` jest tylko w ścieżce v1/`annotation`). Firebase CLI rozwija `name@` wyłącznie przy tworzeniu/aktualizacji funkcji (`gcp/cloudfunctionsv2.js:174`, `proto.formatServiceAccount`). Natomiast przy nadawaniu dostępu do sekretu (`deploy/functions/ensure.js`/`secretsToServiceAccounts`: `const sa = e.serviceAccount || …`) używany jest surowy skrót `fn-consent@`, stąd `setIamPolicy … 400 Invalid service account (fn-consent@)`. Poprawka (pełny adres już w manifeście) omija tę lukę w CLI.

**Discovery (analiza kodu przy `firebase deploy --project X`).** `deploy/functions/prepare.js` (ok. l. 543–551): `firebaseEnvs = loadFirebaseEnvs(firebaseConfig, projectId, …)` → `{ FIREBASE_CONFIG, GCLOUD_PROJECT: projectId }` (`lib/functions/env.js:295-299`), a następnie `runtimeDelegate.discoverBuild(config, { ...userEnvs, ...firebaseEnvs, … })`. `spawnFunctionsProcess` (`runtimes/node/index.js`) przekazuje te zmienne jako środowisko procesu Node (`env = { ...envs, … }`). `projectId` pochodzi z `--project`/aliasu (`.firebaserc`: `dev`/`default` → `tamitu-dev-tadecode`). Czyli `process.env.GCLOUD_PROJECT` jest ustawione, gdy `index.ts` jest importowany podczas analizy. Dodatkowy dowód wprost: SDK 7.4.0 w `serviceAccountFromShorthand` oraz CLI w `populateDefaultParams` polegają na tej samej zmiennej (`encoding.js:42-45` rzuca błąd, gdy `GCLOUD_PROJECT` jest nieustawione) – PR stosuje ten sam kontrakt i ten sam fail-closed.

**Runtime (Cloud Run).** `prepare.js` (ok. l. 209, 230, 242): `envs = { ...userEnvs, ...firebaseEnvs }` → `wantBackend.environmentVariables = envs` → `endpoint.environmentVariables` każdej funkcji; `GCLOUD_PROJECT` jest więc zmienną środowiskową wdrożonej funkcji (jest na liście zarezerwowanych kluczy, tj. zarządza nią CLI, nie użytkownik). Moduł `index.js` ładuje się przy starcie instancji i wywołuje `serviceAccountFor` ponownie – wartość jest dostępna. Gdyby jej zabrakło, instancja nie wystartuje (głośna awaria, nie ciche konto domyślne).

**Emulator / `singleProjectMode`.** Emulator Functions ustawia `GCLOUD_PROJECT` w środowisku procesu funkcji (`emulator/functionsEmulator.js` `getSystemEnvs`, l. 1007) z `--project`; `singleProjectMode` dotyczy tylko ostrzeżenia o niezgodności projektu klienta i nie zmienia tej zmiennej. Emulator uruchomiony bez projektu (`--project` brak) dostanie wyjątek – akceptowalne. Testy reguł Firestore (`emulators:start --only firestore`) nie ładują funkcji.

## Sprawdzone – zgodne

- **Wartość:** dev → `fn-consent@tamitu-dev-tadecode.iam.gserviceaccount.com`, prod → `…@tamitu-prod-tadecode…`; zgodne z adresami z runbooka P3-03. Bez hard-codowania ID (ten sam kod dla dev i prod).
- **Fail-closed:** brak/pusta/zła forma `GCLOUD_PROJECT` → wyjątek; nigdy `default`/konto compute. Regex identyczny jak reguła Google (6–30 znaków) i jak wcześniejsza kontrola w teście; odrzuca `.`, `/`, wielkie litery, końcowy `-` (brak wstrzyknięcia w adres).
- **Testy (`service-accounts.test.ts`):** `vi.hoisted` ustawia `GCLOUD_PROJECT` przed importem `index.ts` (hoisting zapewnia kolejność); jedyny plik testów importujący `src/index` – pozostałe testy nie zależą od zmiennej. Testy: pełne adresy dev/prod, nigdy skrót `name@`, brak projectu i pusty ciąg (wyjątek), złe ID, mapowanie wszystkich 4 funkcji, region. Parametr `env` z domyślnym `process.env` czyni funkcję testowalną bez mutowania globalnego stanu. Funkcja pomocnicza `serviceAccountEmail` (tylko testowa) usunięta – kod produkcyjny sam robi to, co dokumentowała.
- **Bezpieczeństwo/RODO:** brak sekretów, kluczy i danych osobowych; nazwy projektów są już publiczne w `.firebaserc`. Brak nowych zależności, uprawnień IAM ani zmian kosztów. Zasada najmniejszych uprawnień (SEC-20) zachowana.
- **Wpis przekazania** zgodny z `.farm/workflows/handoff.md`; zgłasza do orkiestratora aktualizację wiersza SEC-20 w planie TAM-84.
